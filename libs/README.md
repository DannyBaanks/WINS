# WINS libraries

WINS does not run Windows DLLs. Each DLL a program imports is answered by native
code. This directory names those pieces as **libraries**, the way a distribution
names packages: `wins-d3d9 0.1.0` instead of "the graphics code". That gives users,
models and bug reports one vocabulary, and it makes the opposite visible: **which
Windows DLLs WINS has no library for**, compared with what real programs import.

| file | what it is |
|---|---|
| `native/wins_libs.zig` | **The registry. Source of truth.** One entry per library: name, version, the DLLs it answers for, the loaders that bind it, its source files, status, summary, evidence. |
| `libs/registry.json` | The registry as JSON, generated by `winrun32 --libs`. Do not edit. |
| `libs/GAPS.md` | Generated report: programs measured, DLLs WINS lacks, unresolved imports per library. Do not edit. |
| `libs/gaps.tsv` | The complete list behind `GAPS.md`: one row per unresolved import. |
| `tools/gen_libs.sh` | Regenerates the three files above from the loaders. |
| `tools/check_libs.sh` | Fails if the registry is stale or names a missing source file. |

## Reading a library entry

- **`status: exercised`** means a real program's run went through the library and
  `evidence` says which run. **`unexercised`** means exports exist and nobody has
  recorded a run. There is no "complete": WINS has not implemented the whole of any DLL.
- A library is **not** a module boundary in the code. Several libraries share a file
  (`winrun_extra_dlls.zig`), and one (`wins-user32`) has an i386 and an x86-64 implementation.
  `sources` lists every file involved.
- **Resolved is not working.** `winrun32 --imports` says whether WINS has an answer for
  an import. Whether the program then behaves as on Windows is what `evidence` and the
  tests are for, and an import inventory is never proof of a port (see `AGENTS.md`).

## Versions

`MAJOR.MINOR.PATCH`, per library, in `native/wins_libs.zig`.

- **PATCH**: a fix that makes something behave more like Windows without adding surface.
- **MINOR**: exports added, or a feature implemented (a new interface, a mixer, a query type).
- **MAJOR**: behaviour a working program relied on changes. None yet: every library is 0.x.

Bump the version **in the same commit** that changes the library, and say why in the
commit message. The loaders print the versions a run used (`[WINS:libs] used: ...`) at
the top of every log, so a log is enough to say what ran. `tools/check_libs.sh` notes
libraries whose sources changed after the registry was last edited, as a reminder.

Baseline: everything that existed when the registry was created is `0.1.0`; earlier history
is in `git log`. A version is a label for a state, not a promise of compatibility.

## Commands

```
tools/build_all.sh /tmp/wins-build              # a new, empty directory
/tmp/wins-build/winrun32 --libs                 # the registry, JSON on stdout
/tmp/wins-build/winrun32 --imports prog.exe     # every import slot: resolved? which library? (does not run it)
tools/gen_libs.sh /tmp/wins-build [PE ...]      # regenerate registry.json, GAPS.md, gaps.tsv
tools/check_libs.sh /tmp/wins-build             # is the registry current?
```

`--imports` and `--check` only map the image and resolve its imports; nothing from it runs.
Even so, treat the images as untrusted data.

## Reading `GAPS.md`

1. **Programs measured**: i386 programs through `winrun32` (every slot), x86-64 programs
   through `winrun` (console) or `winrun_gui` (window) with `--check`, which reports the
   unresolved imports and a total but no per-DLL breakdown. Programs a loader refuses before
   resolving imports (delay-import tables, DLLs) are listed as *not measured*, with the reason.
2. **DLLs WINS has no library for**: the shopping list. An **empty table is not "nothing
   missing"**: it only reflects what could be measured. A DLL can appear here even though
   code for it exists: at the time of writing, `lookupUxtheme`, `lookupImm32`,
   `lookupComdlg32`, `lookupDwmapi` and `lookupWininet` in `winrun_extra_dlls.zig` are
   reached only by the fuzzer, not bound by any loader. (`grep -F 'lookupX(' native/*.zig`
   tells you; the report is regenerated, this sentence is not.)
3. **Unresolved imports of DLLs WINS has a library for**: the work list per library.

The fall-through tables in `winrun32` answer some symbols by name whatever DLL they were
imported from, so an import can resolve without being attributed to a library. The report
counts those as "resolved by name".

`GAPS.md` was made from one machine's corpus (`corpus/` holds symlinks to local files,
none versioned) and the Fallout: New Vegas executable. Rerun the script to measure your own.

## Adding a library

1. Implement it (a `lookup...` table that `resolveImport` in `native/winrun32.zig`, or
   `winrun_impl.zig` for x86-64, actually calls) and test it against an independent oracle
   where you can (`native/testdata/*_probe.c` against Proton), with a negative control.
2. Add an entry to `native/wins_libs.zig` (`unexercised` until a run is recorded; then
   `exercised` with `evidence`). `zig test native/wins_libs.zig` enforces the invariants:
   semver, unique names, one library per DLL, lowercase `.dll` names.
3. `tools/build_all.sh <new dir>`, then `tools/gen_libs.sh <that dir>` and commit
   `native/`, `libs/` together.
