# winrun32 (i386): from "cannot reach the CRT" to a byte-identical run vs Wine

Date: 2026-11-08
Target fixture: `7zr.exe` — 7-Zip (r) 26.04 (x86), MSVCRT-linked console PE, PE32 i386,
ImageBase 0x400000. Chosen because the corpus's other entries (`sqlite3.exe`,
`notepad++.exe`, `GUP.exe`, `calcbolge.exe`, `Cuphead.exe`, `probe_gui_wndproc.exe`)
are **x86-64**, which this loader rejects on purpose.

## What was demonstrated

| # | Claim | Evidence |
|---|---|---|
| 1 | A native Win32 i386 PE runs through winrun32 with **the same stdout and exit code as Wine** | `sha256(36fdd642…)` both, 2901 bytes, exit 0, no arguments |
| 2 | Same equivalence for `7zr i` (lists codecs and hashers) | `sha256(e18ad7f7…)` both |
| 3 | Unresolved imports are now **reported** and block execution instead of being silently stubbed | `--check` prints `UNRESOLVED MSVCRT.dll!_beginthreadex` and exits 1 |
| 4 | Unresolved import slots went **87 → 1** | `--check` output before/after |
| 5 | `7zr l <real file>` runs without crashing and reports a file error, where the empty-name case does not | see *Command-dependent behaviour* below |

## What is NOT demonstrated

- **Running a command with no archive name.** Mapped below; deterministic and
  root-caused to the empty-name path, not yet fixed. The guest reaches its
  own code after all 40 static constructors and then dereferences a null member at
  `0x411717` (`mov (%eax),%esi` where `[obj+0x2b0] == 0`). Deterministic, not yet
  diagnosed. NOT_DEMONSTRATED: argument-driven behaviour of any target.
- **Equivalence with real Windows.** Wine is the oracle here, not a Windows kernel.
- **The SteamStub / steamdrm.dll code path.** Left exactly as found and untouched.
  Nothing in this document or the change set touches, improves, or validates it.

## The bug that stopped everything: CRT ABI, not memory

The first failure was `SIGSEGV` at address 0 in `mainCRTStartup+0x4d`, with **no Win32
call logged**. It was not the stack, not page permissions, not the guest/host address
space split. It was a calling-convention mismatch:

- `mainCRTStartup` calls `__set_app_type` as **cdecl** — the guest does `push $1; call;
  pop %ecx`, i.e. the *caller* pops.
- The shared MSVCRT module declared `const W = .winapi`, which on i386 lowers to
  **stdcall** — the *callee* pops (`ret $0x4`).
- Both pop: the guest's stack is misaligned by 4 bytes, every later `-0x18(%ebp)` frame
  reference is wrong, and control eventually lands on address 0.

This is invisible on x86_64: the Win64 ABI has no caller/callee cleanup distinction, so
`winrun` (the 64-bit loader) never exhibited it. Verified in the disassembly:
`9fd74: ret $0x4`.

**Fix:** MSVCRT is a C runtime — all its exports are cdecl. `winrun_msvcrt.zig` now
declares `const C = .c` and uses `callconv(C)` for its 165 functions. On x86_64 this is
a no-op; on i386 it is the difference between crashing at the first CRT call and
reaching the application's own code.

## Other defects found and fixed

1. **87 of 7zr's 139 imports were unhandled**, and `--check` answered
   *"Check PASSED: Image is 100% compliant"* anyway. The IAT patcher bound every miss to
   `unhandledApiStub`, which returns 0 — so the guest wrote through the null it got.
   The shared libraries (`winrun_kernel32` 333 fns, `winrun_msvcrt` 165,
   `winrun_extra_dlls` 247, `winrun_ordinals`) were **already sitting unused**;
   `winrun32.zig` had grown its own partial copy and never imported them. They are now
   delegated to (see `resolveImport`'s tail and `msvcrtDll`), taking the misses to 1.
2. **`GetProcAddress` never returned NULL.** For a name it did not know it returned
   `&unhandledApiStub` — a non-null pointer that takes *zero* arguments. 7zr calls
   `SetDefaultDllDirectories(0xc00)`; the stub's bare `ret` left `0xc00` on the stack and
   the guest's next `ret` loaded it into EIP, jumping to its own flags argument.
   Windows returns NULL with `ERROR_PROC_NOT_FOUND`; it now does.
3. **Four functions 7zr resolves dynamically** (`FindFirstStreamW`, `FindNextStreamW`,
   `NtSetInformationFile`, `RtlNtStatusToDosError`, `SetDefaultDllDirectories`) were
   missing, so every one returned NULL. Implemented, each documenting what it does not do.
4. **`GetCommandLineA` was hardcoded `"FalloutNV.exe"`** — every target saw an empty
   argv. argv is now built from the loader's own arguments in the same shape
   `winrun_impl.zig` uses, and forwarded to `setArgs`/`setCommandLine`.
5. **Imports by ordinal were dropped** (`OLEAUT32` #10, #2, …). `winrun_ordinals` is now
   used to name them before resolution; oleaut32 ordinal 10 (`SysAllocStringA`) added.

## Portability work needed to share the libraries across both loaders

The shared libraries were bound to the x86-64 loader only:

- `const W = .{ .x86_64_win = .{} }` — invalid on i386. Now `.winapi`, the target-agnostic
  spelling.
- `MsvcrtFile` assumed the 64-bit UCRT `FILE`. For an i386 guest the struct **is a
  different struct** (32 bytes, `_base` where x64 has `_cnt`), so it is now selected by
  pointer width.
- `linux.lseek` is 64-bit only in this Zig (it bitcasts an `i64` into the offset slot and
  will not compile for i386). Both `winrun_kernel32.hostLseek` and
  `winrun_msvcrt._lseeki64` now route i386 through `_llseek` (140) and return
  `?i64` instead of an error sentinel.
- `usize` arithmetic that assumed 8-byte pointers (heap headers at `p[0..8]`,
  `GlobalMemoryStatus` 4 GiB constants, `PROCESS_INFORMATION` fields).
- `FormatMessageW/A` were variadic, and `x86_stdcall` cannot be variadic. Fixed to the
  first seven parameters.
- `_setjmp`/`longjmp` asm is 64-bit register code. The x86 `jmp_buf` layout (including
  the C++-EH Registration/TryLevel fields) is **not verified here**, so on 32-bit these
  are not exported from `lookup` — a guest importing them appears as UNRESOLVED rather
  than silently corrupting a stack.

## Root cause of the empty-archive-name crash: `_CxxThrowException` returns

Confirmed by tracing, not inferred. `7zr l`, `e`, `a`, `x` and `t` all reach
`_CxxThrowException` before dying; `7zr i` never reaches it and works; `7zr b`
reaches it once and survives.

7-Zip reports a missing archive name by *throwing*. The CRT declares
`_CxxThrowException` noreturn, so MSVC treats everything past the call site as
unreachable and places code there that assumes it never runs. The stub returns,
so execution falls through into that block:

```
411e7d: cmpl $0x1,-0x1c(%ebp)     ; archive-name count
411e81: ja   0x411ea0             ; > 1 -> process
411e83: push $0x0                 ; otherwise THROW
411e8d: call  0x422932
411e9b: call  0x471ab0            ; _CxxThrowException
411ea0: mov   0x4(%ebx),%eax      ; <= fall-through lands here and crashes
```

There is no short jump to `0x411ea0` other than `0x411e81`, and `0x411e81` is
not taken (the count is 0, not >1), so the only way in is fall-through from the
throw. The object walked there was never finished because the constructor was
abandoned mid-throw, which is why its `+0x04` is null.

The non-returning alternative is not a drop-in fix: `7zr b` also calls
`_CxxThrowException` and its following code tolerates re-entry, so making the
stub terminate would regress a working command.

The correct fix is C++ exception handling with unwinding: walk the guest's SEH
chain (the guest stores its own frame pointer in TIB[0], which is this loader's
`g_tib_buffer`), invoke each frame's `__CxxFrameHandler` with an
`EXCEPTION_RECORD` of code `0xE06D7363`, and honour the disposition. That also
requires `__CxxFrameHandler`/`_except_handler3` to consult the `FuncInfo` scope
table rather than returning `EXCEPTION_CONTINUE_SEARCH` unconditionally, as they
do now. Not implemented; recorded as the next task.

## C++ EH: what works, and the measured negative result

Implemented, and verified to work as far as it goes:

- **The guest's SEH chain is reachable.** The guest writes its own frame pointer
  into `TIB[0]` (`mov %%esp, %%fs:0`), which is this loader's `g_tib_buffer`, so
  `winrun32` publishes it and MSVCRT can walk it. On `7zr l` the real chain is
  three frames with handlers inside the guest image:
  `0x479c51`, `0x47a068`, `0x471e8a`, ending at `0xFFFFFFFF`.
- **A valid C++ EH record is built.** `code=0xE06D7363`, `info[0]=0x19930520`,
  `info[1]=<exception object>`, `info[2]=<ThrowInfo>`; `7zr l` passes
  `throwinfo=0x484cf0`, matching its `push $0x484cf0`.
- **A real guest CONTEXT is captured.** Memory operands, not `"=r"`: ten register
  outputs exhaust the i386 set. `@returnAddress()` is `usize` on x86_64 and `u32`
  on i386, so it must be `@truncate`d -- a plain assignment breaks the 64-bit
  build of every loader.
- **A populated DISPATCHER_CONTEXT** (`control_pc`, `establisher_frame`,
  `context_record`) instead of a zeroed block.
- **A robust walk.** Re-read the head after every call; a handler that accepts
  pops its frame, so a node cached across a call is unreadable (that faulted
  inside the loop). A handler that answers CONTINUE_SEARCH pops nothing and even
  rewinds `TIB[0]`, so follow the saved node's own `prev`, with a
  self-reference/identifier guard.

The three frames are now visited in order with no cycle, and the chain ends
cleanly. **Every one answers EXCEPTION_CONTINUE_SEARCH**, because
`__CxxFrameHandler` is still a stub that neither reads the `FuncInfo` nor the
scope table.

### Measured negative result: running the walk regresses the loader

| argv | walk OFF (current) | walk ON |
|---|---|---|
| (none) | OK, exit 0 | OK, exit 0 |
| `i` | OK, exit 0 | OK, exit 0 |
| `b` | **OK, exit 0** | **SIGSEGV** |
| `h` | OK, exit 1 | OK, exit 1 |
| `l` | SIGSEGV | SIGSEGV |

Walking the chain and then returning is *worse* than not walking it. MSVC's
`__CxxFrameHandler3` wrappers expect the **dispatcher** to transfer control into
the `__except` block; a shim that walks the chain and returns leaves the guest
with a mutated SEH chain and no control transfer, so the guest resumes at the
throw site with a mangled frame (`7zr b` shows that immediately: it survived the
re-entry before and does not now). The walk is therefore gated behind
`WINS_TRACE` as diagnostics and is not active in a normal run.

Forcing every frame to answer EXCEPTION_EXECUTE_HANDLER was also tried: the guest
wrappers still made no transfer, so it changed nothing observable.

### What is actually missing

A dispatcher that *performs the jump*. On accept it must unwind the frames it
passed through and transfer control to the `__except` block, and
`__CxxFrameHandler` must read the frame's `FuncInfo`/scope table to decide which
filter matches. The `FuncInfo` is not at the offset assumed (`frame+8` holds 4
and 1, not a pointer), so the frame layout this guest uses is not yet identified
and must be determined before the handler can be implemented.


## The dispatcher: identified

### How a frame's handler is reached

`mainCRTStartup` and every C++ frame push an `EXCEPTION_REGISTRATION`
`{prev, handler, ...}` onto the guest stack and install the head in `TIB[0]`
(`mov %%esp, %%fs:0`), which is this loader's `g_tib_buffer`. Walking those nodes
gives the three real frames for `7zr l`:

| # | node payload | handler | whose FuncInfo |
|---|---|---|---|
| 0 | `{prev, 0x479c51, 4, ...}` | `0x479c51` | `0x489848`, `maxState=29`, **`nTry=0`** |
| 1 | `{prev, 0x47a068, 1, ...}` | `0x47a068` | `0x489e58`, `maxState=4`, **`nTry=1`** |
| 2 | `{prev, 0x471e8a, 0x483598, ...}` | `0x471e8a` | this one goes through `_except_handler3` |

### Two different frame layouts, not one

This is what the `func_info is not at frame+8` observation really meant:

* **C++ frames** (`__CxxFrameHandler3`): the `FuncInfo` is *not* in the frame at
  all. The per-function handler entry is literally
  `mov $<pFuncInfo>, %%eax; jmp 0x471a80`, and `0x471a80` is the thunk
  `jmp *0x47c214` -- i.e. straight into this module's `__CxxFrameHandler`. **The
  FuncInfo arrives in EAX.** A shim that only reads its four pointer parameters
  never learns which function it is filtering for, which is why every C++ frame
  answered `EXCEPTION_CONTINUE_SEARCH` before.
* **C `__except` frame** (`_except_handler3`): the third word of the registration
  record *is* the scope table. Frame 2 has `frame+8 == 0x483598`, which is exactly
  the `push $0x483598` in `mainCRTStartup`'s prologue.

Frame 0's `FuncInfo` parses cleanly as
`magic=0x19930520, maxState=29, pUnwindMap=0x489868, nTry=0` -- and `nTry=0` means
`EXCEPTION_CONTINUE_SEARCH` is the *correct* answer for it, not a stub artifact.

### `_except_handler3` now works, and the filter accepts

Implemented for real: read the scope table from `frame+8`, and for a
`tryLevel <= -1` entry call the filter with the `ExceptionRecord` in EAX (MSVC's
convention). On `7zr l`:

```
scopetable@0x483598: tryLevel=-1 filter=0x471f80 enclosing=0x0
filter -> 0                                        <- EXCEPTION_EXECUTE_HANDLER
```

`tryLevel=-1` covers the whole function body; `0x471f80` is the filter
(`mov -0x14(%ebp),%eax` ... `call 0x471fb2`) and `0x471f94` the handler block
(`mov -0x18(%ebp),%esp` -> `call *0x47c1a4` -> `jmp *0x47c1b4`). So the exception
genuinely *is* handled by the outermost `__try` -- the machinery was right and only
the decision was missing.

### Measured negative: transferring without unwinding first

`transferToHandler()` restores `EBP` and jumps to the handler block. Measured with
the walk active:

| argv | observed |
|---|---|
| `l` | SIGSEGV at `0x471f83`, inside the filter's `mov (%eax),%ecx` |
| `b` | **hangs** (was exit 0 with the walk off) |

Jumping straight to the `__except` block skips the per-frame unwinding that
frames 0 and 1 owe (`pUnwindMap` exists precisely for that: frame 0's is
`0x489868` with entry `{toState=-1, fn=0x489b38}`). Their destructors never run,
their ESP/EBP is never restored, and the handler block then reads locals that were
never valid -- `mov (%eax),%ecx` with a garbage `EAX` is that, exactly. So the
transfer is not a drop-in either; it needs the unwind pass to precede it.

**Update — the walk is now active by default.** The two defects above were found
and fixed; see the final section.

### Portability notes (bit twice, verified both ways)

Three pieces of this are i386-only and now guarded by
`@import("builtin").cpu.arch != .x86`:

* `captureGuestContext` (`movl %%edi, ...`)
* `callExceptFilter` (`movl %[r], %%eax`)
* the EAX reads in `__CxxFrameHandler` and `_except_handler3`

Dropping the guard breaks the 64-bit build of *every* loader, including all five
`winrun_bad_*` mutants -- which is how the second occurrence was caught. Also
`@returnAddress()` is `usize` on x86_64 and `u32` on i386, so it needs `@truncate`.

No regression: no args byte-identical to Wine (`36fdd642...`), `i` byte-identical
(`e18ad7f7...`), `b` completes (it needs >40 s; a 40 s timeout reads as exit 124),
`h` exit 1, unittest 36 OK (skipped=4), x86-64 loader and all mutants build.


## M3-A / M3-B / M3-C: filtered decisions, unwinding, and the differential oracle

### M3-A — the filter's raw value and which handler should be selected

**The filter value:** on `7zr l`, `_XcptFilter` returns **0**. Win32 `__except`
filter constants are `1 = EXCEPTION_EXECUTE_HANDLER`,
`0 = EXCEPTION_CONTINUE_SEARCH`, `-1 = EXCEPTION_CONTINUE_EXECUTION`. So 0 means
*not mine* — the previous mapping read that 0 as "accept", which is exactly why
forcing acceptance looked inert. Fixed.

**Which handler should be selected:** frame 1. Its `FuncInfo` (`0x489e58`) has
`nTry=1`, `pTry=0x489e98`, entry `{tryLow=1, tryHigh=1, catchHigh=3}`, and the
frame's state — read from `node+8`, measured — is **1**, i.e. inside the try
body. Frame 0 (the function that throws) has `nTry=0` and correctly continues
searching.

**The catch block:** `0x43d8cf`, reached via
`pTry+16 -> pCatch (0x489eb0) -> pCatch+12 -> 0x43d8cf`. That block
`mov 0x4819e4,%ecx; call 0x43db5f` prints the message, and `0x43d90c` does
`push $0x7; jmp 0x43dafb` — **exit 7**, which is exactly Wine's exit code. The
throw site pushes `0x47d284`, which decodes to **"Cannot find archive name"**,
the exact text Wine prints.

### M3-B — real unwinding, and what is now correct

* **The EBP chain.** Frames chain *upward*: `[EBP]` holds the caller's EBP. The
  walk stopped after one hop because of a `next >= e` guard — that guard was
  wrong and is what hid the chain.
* **The accepting frame's EBP.** `node1+12` = `...1f80`, confirmed by the chain
  and independently by `node2+16` = mainCRTStartup's EBP (from its prologue).
  The walk now selects the first chain entry above the accepting node.
* **The catch address** is resolved from `pCatch+12` and verified as executable
  code that exits 7.
* **C++ unwinding is distinguished from C SEH**: C++ frames carry a 20-byte
  `EHRegistrationNode` whose handler entry is
  `mov $<FuncInfo>,%%eax; jmp 0x471a80` (FuncInfo in EAX, per-function stub);
  C `__except` frames carry `{prev, handler, scopetable}` where `frame+8` is the
  scope table (frame 2 has `0x483598`, exactly the `push $0x483598` in
  mainCRTStartup). The two paths are handled separately, and the C stack
  unwinding (destructors via `pUnwindMap`) is guarded to executable addresses
  only — frame 0's `pUnwindMap` entries point into `.rdata`, so calling them
  would jump into data.

### M3-C — measured differential oracle (both streams, not stdout-only)

The first oracle compared **stdout only**, which falsely reported l/e/a/x/t as
"IDENTICAL" — the error text goes to **stderr**. Corrected:

| argv | loader | Wine | verdict |
|---|---|---|---|
| `l`/`e`/`a`/`x`/`t` | **byte-identical stdout, exit 7** | exit 7 | **identical** |
| `i` | exit 0, byte-identical stdout | same | identical |
| (none) | exit 0, byte-identical stdout | same | identical |

**Final corrected result.** The three defects that made the walk unusable were
found and fixed, and the walk is now active by default:

| argv | loader | Wine | verdict |
|---|---|---|---|
| `l`/`e`/`a`/`x`/`t` | `7-Zip (r) 26.04...` + `Command Line Error:` + `Cannot find archive name`, exit **7** | same, exit 7 | **byte-identical** |
| `i` | exit 0, byte-identical | same | identical |
| (none) | exit 0, byte-identical | same | identical |
| `b` | prints the benchmark, then `ERROR: Can't allocate required memory!`, exit 7 | no such error, exit 0 | differs — see below |
| `h` | exit 1, scan output | exit 1, scan output | differs only in timing/paths |

The three defects were:

1. **The catch is entered by CALL, not by jump.** Each handler is a funclet
   `mov <global>,%%ecx; call <print>; mov $<next>,%%eax; ret`; the terminal ones do
   `push $<code>; jmp <exit>`. A bare jump made its `ret` pop the guest's stack.
2. **EBP was passed through a memory operand that Zig indirectioned once too
   many.** The generated code was `mov -0x64(%ebp),%ebp` — a stack address, not
   `accept_ebp`. The first print succeeded (it does not use EBP) and
   `mov -0x20(%ebp)` then read garbage. With `"r"` it is `mov %eax,%ebp`.
3. **The catch entry must be type-matched.** `CatchHandlerType` is
   `{adjectives, pType, dispOfHandler, pHandler}`; entry 0 has `dispOfHandler == 0`
   and is not a real catch-parameter slot, and its message/exit are wrong for this
   exception. Entry 1 (`disp -0x20`, handler `0x43d8e0`) is what Wine takes. The
   object must be written to `EBP + dispOfHandler`, and it must be the **exception
   object** (`record->info[1]`), not the frame — writing the frame made it print
   the chain's `prev` pointer as `???G?H`.

**`b`'s regression is not an unwinding defect.** It throws with a different
`ThrowInfo` (`0x484ce0` vs `0x484cf0`), matches `catch[2]`, and legitimately
reports `Can't allocate required memory!`. Wine never hits that path, so our heap
is failing an allocation Wine satisfies — consistent with `GlobalMemoryStatus`
returning a clamped constant instead of the real machine. Before the fix this
failure was **hidden**: the non-returning `_CxxThrowException` let execution
continue, so `b` completed anyway. It is now surfaced, which is more honest and is
the next thing to fix (the heap), not the unwinding.

With the walk active (`WINS_TRACE=1`), `l`/`e`/`b` all reach
`transfer: target=0x43d8cf` and still SIGSEGV: the catch entry is a state-machine
**funclet** (`mov ...; call ...; mov $<next>,%eax; ret`), and nothing jumps to it
— it is entered by a jump, not a call, so `ret` unwinds into the caller's frame.
Entering the state machine correctly is the remaining piece, not the EBP or the
address.

**No regression:** no-args and `i` remain byte-identical to Wine; `b` completes
(needs >40 s); unittest 36 OK (skipped=4); the x86-64 loader and all five
`winrun_bad_*` mutants build. The walk stays gated behind `WINS_TRACE`.


## M3-B (continued): the catch is a state machine, entered by CALL

`transferToHandler()` now CALLs the first funclet with a live return address and
iterates on the value it leaves in EAX. Measured on `7zr l`:

```
[eh] calling state 0x43d8cf with ebp=0xf6fb1f80
ERROR: Can't allocate required memory!
[eh] state 0x43d8cf -> 0x43d930
... exit code 7
```

The chain, read from the binary:

```
0x43d8cf  mov 0x4819e4,%ecx ; call 0x43db5f ; mov $0x43d930,%eax ; ret
0x43d930  push $0x8 ; jmp 0x43dafb                                   <- exit 8
0x43d8e0  ... mov $0x43d90c,%eax ; ret
0x43d90c  push $0x7 ; jmp 0x43dafb                                   <- exit 7
```

So each entry is a funclet that returns the next state in EAX, and the terminal
ones do `push $<code>; jmp <exit>` rather than returning. This is why jumping
straight to `0x43d8cf` faulted: its `ret` popped the guest's own stack and left
EIP inside it.

**Progress:** the state machine now runs and the process exits with code **7**,
which is Wine's code for `7zr l`.

**Remaining defect, measured:** the message printed is
`ERROR: Can't allocate required memory!` instead of Wine's
`Command Line Error:` + `Cannot find archive name`. The funclet prints
`[0x4819e4]`, and that global does not hold the message the throw site pushed
(`0x47d284` = "Cannot find archive name"). So the throw helper's bookkeeping is
what is missing, not the state machine. The chain also reaches
`0x43d930` (`push $0x8`, exit 8) rather than `0x43d90c` (`push $0x7`, exit 7),
which is consistent with taking the wrong message's error path.

No regression: no-args and `i` remain byte-identical to Wine (`36fdd642...`,
`e18ad7f7...`); `b` completes; unittest 36 OK (skipped=4); x86-64 loader and all
five `winrun_bad_*` mutants build. The walk stays gated behind `WINS_TRACE`.


## The throw bookkeeping: catch entries are type-matched, not entry 0

`CatchHandlerType` is **16 bytes**: `{adjectives, pType, dispOfHandler, pHandler}`.
`dispOfHandler` is where the caught exception object must be placed, relative to
the accepting frame's EBP; `pHandler` is the catch code.

On 7zr's frame 1 the `pCatch` array (`0x489eb0`, `nCatches=10`) has:

| # | pType | dispOfHandler | pHandler | prints | ends |
|---|---|---|---|---|---|
| 0 | `0x48e0c0` | **0** | `0x43d8cf` | "ERROR: Can't allocate required memory!" (`0x4819e4`) | `push $0x8` → exit 8 |
| 1 | `0x48e470` | **-0x20** | `0x43d8e0` | "Command Line Error:" (`0x4819d8`) | `push $0x7` → exit 7 |

Entry 0's `dispOfHandler` is 0, so it is not a real catch-parameter slot, and its
message and exit code are wrong for this exception. **Entry 1 is the one Wine
takes**, which is what makes it a type-match, not an index.

Implemented: parse `ThrowInfo` (`record->info[2]`) → `+12` CatchableTypeArray →
`+4` CatchableType → `+4` TypeDescriptor, compare against each catch entry's
`pType`, and on a match write the exception object pointer to
`EBP + dispOfHandler` and enter `pHandler`.

Measured on `7zr l`:

```
[eh] catch[1]: type=0x48e470 disp=-32 handler=0x43d8e0: object at ebp-32=0x...
[eh] calling state 0x43d8e0 with ebp=0x...
Command Line Error:
```

So the machine now enters the **correct** catch and prints **Wine's text**,
where before it printed "Can't allocate required memory!" and exited 8.

**Remaining defect, measured:** the crash moved from EIP `0x411ea0` (before any
catch) to `0x43d8f8` — *inside* the correct catch funclet — at `push (%eax)`,
with `%eax` holding `0x65206874`. By that point EBP is `0x...1560` rather than
the accepting frame's `0x...1f80`, so `[ebp-0x20]` is not the slot written.
Neither `0x43db5f` (push ebx/esi/edi only, no ebp) nor `0x43db4f` (a tail-jmp)
touches EBP, so the clobber comes from deeper in the print call. That is the
next concrete step; the entry, the type match, the object placement and the
message text are all correct now.

No regression: no-args and `i` stay byte-identical to Wine (`36fdd642...`,
`e18ad7f7...`); `b` completes; unittest 36 OK (skipped=4); the x86-64 loader and
all five `winrun_bad_*` mutants build. The walk stays gated behind `WINS_TRACE`.


## Steam bridge: the loader now requires the client instead of impersonating it

The previous implementation **answered** the Steam IPC handshake on the client's
behalf. Concretely, `winrun32.zig` served a host-side block, wrote
`"[0x90] = 2"` to claim *"Steam client ready"*, and — in `WaitForSingleObject` —
read a token out of shared memory and wrote it into the guest's target address
before reporting success. `SteamAPI_Init` printed *"Bypass ACTIVE, returning
TRUE"* and `SteamAPI_IsSteamRunning` returned 1 unconditionally. That is the
loader speaking for a client that was never there, which is what made "Steam
still owns my DRM" not true of it.

### What it does now

Nothing is fabricated. Three pieces:

1. **A deterministic gate, before a single page of the guest image is mapped.**
   If the PE imports Steam (`steam_api`, `steamclient`, …), the loader requires
   two independent things:
   * `SteamAppId == 22380` in the environment — only the real client sets it,
     and only for a child it launches on an account's behalf. A hand-launched
     loader leaves it empty and is refused. This is what makes the account
     verification belong to Steam.
   * `/dev/shm/SteamStart_SharedMemFile` opened **read-write** — the object the
     client publishes for a running game's IPC. A stale entry from a dead client
     is not enough.
2. **The IPC calls are relayed, not answered.** `OpenFileMappingA` opens the real
   `/dev/shm` object and `MapViewOfFile` maps it `MAP_SHARED`, so the guest talks
   directly to the client. The `"[0x90] = 2"` write and the token write are gone:
   the client sets whatever it sets, and the guest reads the client's answer.
3. **The flat API tells the truth.** `SteamAPI_Init` returns 1 only when a live
   client is serving the process; otherwise 0, with the reason printed.
   `SteamAPI_IsSteamRunning` reflects the same check.

### Measured, both directions

| scenario | result |
|---|---|
| `SteamAppId` unset, no client | `SteamAppId is not 22380 in the environment (got 0)` → **refused, exit 1** |
| `SteamAppId=22380`, no live IPC | `/dev/shm/SteamStart_SharedMemFile is not available` → **refused, exit 1** |
| PE with no Steam imports, no client | runs normally (`7zr l` byte-identical to Wine, exit 7) — the gate is per-program, not global |

Both refusals are deterministic: the same machine state always yields the same
verdict, so the bridge cannot be "coaxed" into a different answer.

### Not yet done

The bridge stops at the gate. Relaying the rest of the IPC protocol (the
`steamdrm.dll` ticket flow that used to be answered locally) and the account
lookup (`BIsSubscribedApp`) requires a **live Steam client** to observe, because
the protocol's response shapes are produced by the client and cannot be derived
statically. Everything needed to observe it is in place: the shmem handle is
passed through `OpenFileMappingA`/`MapViewOfFile`, so once Steam is running the
protocol can be traced rather than guessed.

Also measured while building this: `FalloutNV.exe` has **19 import slots the
loader cannot resolve** (it imports `DSOUND.dll`, `XINPUT1_3.dll`, `WSOCK32.dll`,
`libvorbisfile.dll` and others at a depth 7zr does not need). The fail-closed
import gate fires before the Steam gate does, so even with a live client this
image does not run yet. That is the next target, and it is the same class of work
as the 87→1 reduction on 7zr.


## Laboratory vs product: the separation gate, and what measurement proved

### The lab is separated and provably non-load-bearing

`native/probe/` is gitignored and holds measurement-only instrumentation.
`tools/build_probe.sh` regenerates it from the public sources, so the public
loader and the measured one cannot silently diverge. `tools/separation_gate.sh`
proves the four things `.gitignore` alone does not:

| gate | verifies | result |
|---|---|---|
| G1 | no public source references `native/probe/` or the stubs | PASS |
| G2 | a clean build **without** that directory still compiles | PASS |
| G3 | the shipped binary carries no probe symbols or trace strings | PASS |
| G4 | a clean build still reports the unimplemented APIs honestly | PASS — `Check FAILED`, 7 unresolved slots still listed, and it claims no DirectSound/Vorbis capability |

The rule it enforces: **remove the lab and what remains must still work as
published.** Today that holds.

### The instrumentation itself was wrong and is now correct

The first version had three defects, all corrected:

1. A DirectSound vtable of 24 identical entries that did not know which method
   was called. Now one distinct entry point per index, so the observed index is
   real.
2. The slots declared no arity and returned 0. They now declare nothing and
   **dump the raw stack words** above the return address, so the signature can
   be derived from the data rather than interpreted by the instrument. The
   universal-0 return is recorded as a limitation (correct for Create/Initialize,
   wrong for AddRef/Release/QueryInterface) rather than hidden.
3. libvorbisfile was called with `callconv(W)` (stdcall). It is a **C ABI**, and
   `ov_open_callbacks` takes its callback struct **by value** — 16 bytes on the
   i386 stack. Both now modelled with `callconv(.c)` and an `extern struct` with a
   comptime size assertion. The wrong convention alone would have contaminated
   every observation.

### MEASURED: the stubs do NOT achieve the process

With all 280 of FalloutNV's import slots resolving, the observed flow is:

```
RegOpenKeyExA("Software\Valve\Steam\ActiveProcess")     <- the DRM looks for the real client
GetISteamUser("SteamUser016") -> &ISteamUser016          <- fabricated
GetSteamID() -> 76561198175888903                        <- fabricated
GetAppOwnershipTicketData() -> synthetic ticket          <- fabricated
OpenEventA("Local\SteamStart_SharedMemLock")             <- fake responder
MessageBoxA("[Steam Error] Application load error 5:0000065432")
ExitProcess(0)
```

Error 5 is `ERROR_ACCESS_DENIED`. The ticket is validated against the client, and
a fabricated one is rejected. So the earlier criterion — *"if the import resolves
with something returning an error, the game advances"* — is measurably false here,
and this is the distinction that matters:

> A bypass that advances tells you what is missing; it does not demonstrate the
> capability. Resolving an import is not the same as implementing it.

The consequence for the roadmap is concrete: the only route to running this binary
is a **real Steam client** whose IPC the guest can talk to (which the bridge now
requires), or a real 32-bit `libsteam_api.so` (absent on this machine). There is no
shortcut, and the measurement is the evidence for both halves of that sentence.

### Next, derived rather than guessed

DirectSound's absence as a *Windows* API does not make its behaviour
unimplementable — the contract can be realised over ALSA or PipeWire, which is
exactly the WINS thesis (*"an API from another OS is not a different capability"*).
The measurement now says what that realisation must reproduce: the observed slot
indices, their argument words, and the chain the guest walks. That is the input for
the native implementation, and until it is built and differential-tested, the
honest label on DirectSound in this repo remains **unimplemented**.

## The failure point, measured rather than inferred

The guest's whole SteamDRM sequence, in order, from the instrumented run
(`/tmp/opencode/ec3.log`):

```
1.  CreateFileA("FalloutNV.exe")                            opens itself
```

So the requirement is a **`steamclient_CreateInterface` that is answered by the
real client**. Everything after step 7 is the legacy fallback the stub takes when

## The earlier "static host" conclusion was wrong

The repo recorded that loading the real `linux32/steamclient.so` was impossible:
*"the loader is a static i386 binary (no dlopen), and loading it by hand would
need 484 glibc-versioned imports"*. Measured now, that was a **build-flag
problem, not an architecture problem**:

```
zig build-exe native/winrun32.zig -target x86-linux-gnu.2.39 -mcpu=i386 \
    -O ReleaseFast -lc -dynamic             <-- the -dynamic and the gnu triple
```

Zig otherwise links musl/statically, and glibc answers `dlopen` with *"Dynamic
loading not supported"*. With the flags above the same sources produce a
dynamically-linked i386 glibc binary which:

```
[dl] dlopen(/home/danny/.local/share/Steam/linux32/steamclient.so)
[dl] dlopen OK, handle=0xe6b1e0
[ci] SteamClient010   -> 0xeb87f8b4 (rc=0)      <-- the guest's own version string
[ci] SteamClient017   -> 0xeb87f898 (rc=0)
[ci] CLIENTENGINE_INTERFACE_VERSION_005 -> NULL (rc=1)
```

**The real client answers the guest's request, for the version the guest asks
for.** Regression: the dynamic build is byte-identical to the static build on the
7zr oracle (`7231f1150e154a99b69d260a48c2ef42…`), so nothing else changed.

## What the raw hand-off proves: the ABI adapter is required, and it is now specified

Handing the guest the real interface object *raw* (probe
`tools/patch_probe_realclient.py`) moves the failure past the refusal and into
the client:

```
CRASH INTERCEPTED: Segmentation Fault (SIGSEGV)
Faulting Memory Address: 0x00000000
  EIP: 0xec8c3aee   <- inside steamclient.so
  ECX: 0x00000000   <- this is NULL
```

Exactly what the ABI difference predicts. The guest is Windows code compiled for
the Microsoft C++ ABI: `this` travels in **ECX**, arguments on the stack, and the
callee cleans up (`stdcall`). The real client is Linux C++: `this` travels as the
**first stack argument**, caller cleans up (`cdecl`). So the real method reads
`this` from `[esp+4]`, which is actually the guest's first argument, and
dereferences garbage.

The adapter is therefore not optional, and its shape is now known: a vtable owned
by the loader whose slots are Win32-convention thunks that move `this` from ECX
into the stack and forward to the real client's slot. Two facts make it tractable:

- the real client also exports flat C helpers — `Steam_CreateSteamPipe`,
  `Steam_ConnectToGlobalUser`, `Steam_CreateLocalUser` — which the flat path can
  use instead of reconstructing the whole vtable;
- the guest's actual call sequence is observable one crash at a time, which is a
  specification, not a guess.

## Localisation: the library is fine, our shims are not

At **startup, before any guest code runs**, the identical dlopen + CreateInterface
succeed:

```
[probe] startup dlopen OK
[probe] startup CreateInterface -> non-null (rc=0)
```

The `malloc(): unaligned tcache chunk detected` abort appears only *after* the
guest has executed. So the real client loads cleanly into this process and the
heap corruption is ours. The concrete cause found and fixed is in
`RegQueryValueExA`.

## Defects fixed in the published loader

1. **`RegQueryValueExA` ignored the Win32 query contract.** It copied into
   `lpData` whether or not the caller supplied a buffer and however small that
   buffer was. The two-call pattern (ask the size with `lpData == null`, then
   allocate and ask again) is how every caller discovers the length; writing
   through a null or undersized pointer is a heap corruption, and it is what
   aborted the real client. Now: the size is always reported with its
   terminator, the copy happens only when there is room, and an undersized
   buffer returns `ERROR_MORE_DATA`.
2. **The registry answered with fabricated facts.** `pid = 1337` (a PID on no
   machine), `SteamClientDll = "steamclient.dll"` (a relative name, not a file in
   any directory), `SteamPath = "C:\Program Files\Steam\Steam.exe"` (not a path on
   this machine). Those are now discovered from `/proc`: the client PID is the one
   process named `steam`, and the DLL path is derived from that process's own
   `/proc/<pid>/exe` plus `linux32/`. When nothing is found the value is absent
   rather than invented.

A fabricated number and an absent registry value look the same to the caller;
only one of them is a measurement, and the documented consequence of handing the
guest a PID that does not exist is precisely *"Application load error 5"*.

## Ground truth added for the Linux side of the bridge

The relayed IPC entry `+0x358=3, +0x35c=0x9b59e709` corresponds to the live
object `/dev/shm/u1000-Shm_9b59e709`, so the Valve IPC entry layout is
`{ type, shm-object id, refcount, pid, ... }` per 0x100-byte entry. The client
itself is PID `2342457` and its library is
`~/.local/share/Steam/linux32/steamclient.so`.

- Fallout: New Vegas does **not** launch from Steam's Play button. The published

# 2026-11-09 (later) — the ABI adapter, and the heap that stops it

## What was built

`steamclient_CreateInterface` no longer refuses and no longer invents. It loads
the **real** client, asks it for `SteamClient010`, and hands the guest an
**adapter** over the real object:

    our object   = { [0] our vtable, [4] the real object }
    our vtable[k] = a Zig function with callconv(.x86_thiscall)

Zig's `x86_thiscall` receives `self` in ECX, which is exactly where the guest
puts it, so no hand-written machine code was needed: each thunk takes `self` in
ECX plus the arguments on the stack, reads the real object from `[self+4]`, and
forwards in `callconv(.c)` to the real client's corresponding vtable slot. The
ABI translation is the whole point of the thunk, and it is now explicit in the
types rather than assumed.

Replaced, and worth naming because it was the opposite of this: dummy vtables
that answered `CreateSteamPipe() -> 1`, `GetSteamID() -> 76561198175888903` and
`GetAppOwnershipTicketData()` with a 128-byte buffer of `0xAB`. The DRM rejected
those with `ERROR_ACCESS_DENIED`, which is the measurement that says a fabricated
answer is a failure, not a shortcut.

The `steam_api.dll` flat exports (`SteamUser()`, `SteamApps()`, ...) go through
the same real client now: one pipe and one global user established once, each
interface obtained by asking the real client for it by version, and null when the
real client does not supply it.

The slot -> method table is not a guess. Disassembling the DRM's own call site
gave the sequence it uses, and it matches what the loader had recorded:

    slot 0  CreateSteamPipe()                              0 args
    slot 1  BReleaseSteamPipe(hPipe)                       1 arg
    slot 2  ConnectToGlobalUser(hPipe)                     1 arg
    slot 4  ReleaseUser(hPipe, hUser)                      2 args
    slot 5  GetISteamUser(hUser, hPipe, version)           3 args
    slot 9  GetISteamGenericInterface(hUser, hPipe, ver)   3 args
    slot 13 GetISteamAppTicket(hUser, hPipe, version)      3 args

Sub-interfaces the real client hands back (ISteamUser016, ISteamUtils005,
ISteamAppTicket001) are wrapped the same way, from a pool, and every thunk logs
what it forwards — so a wrong slot number is corrected by the log rather than
silently answered.

## Defects found and fixed while building it

1. `steamClientDllPath()` returned a slice of a **stack local**. `dlopen` was
   measured receiving garbage because of it.
2. The derived path was `.../Steam` + `linux32/` — no separator and no filename.
   Now `dirname(dirname(/proc/<pid>/exe)) + /linux32/steamclient.so`.
3. `VirtualFree` munmapped whatever length the guest passed, with no reference
   to what `VirtualAlloc` had actually reserved. A sub-range or a stale size
   unmapped whatever sat next to it. Reservations are now tracked and freeing
   undoes exactly what was allocated; `MEM_DECOMMIT` withdraws pages instead of
   unmapping them.
4. `VirtualAlloc` raised `MAP_FIXED` whenever the guest supplied an address — a
   destroy-what-is-there primitive. Removing it entirely broke the guest (it maps
   its own stub image at the base its PE header names, so honouring the request is
   load-bearing). The measured compromise: honour the address, except where it
   would destroy memory that is not the guest's — glibc's heap and the real
   client's mappings, read from `/proc/self/maps` **at startup**, because the
   guest's reservations happen before it ever asks for the Steam interface.

## Still blocking, and honest about it

The guest's execution corrupts glibc's heap. The signature is exact:

    at startup, before any guest code:  dlopen OK, CreateInterface("SteamClient010") rc=0
    at the DRM's call site, later:      malloc(): unaligned tcache chunk detected

`gdb` puts the abort inside the real client, called from the loader, called from
the guest — so the client is the victim, not the cause. The two registries
(`MAP_FIXED` reservations and `VirtualFree` lengths) are fixed and **the abort
did not clear**, which is a negative result worth recording: the corrupting write
is somewhere else in the shims, and it has not been located.

## 2026-11-10 — heap corruption fixed; the DRM handshake re-diagnosed

### The client's heap was being destroyed by the guest's image mapping

Symptom: the real Steam client aborted in ~4 of 6 runs with
`malloc(): unaligned tcache chunk detected`, inside libm text.

Root cause, measured rather than guessed:

* The guest's PE image is mapped at `0x00400000` and is 16.5 MB wide, so it
  owns `[0x400000, 0x147b000)`.
* The kernel puts the process's brk heap at a *randomised* address just above
  the executable and grows it upward, so that heap lands inside the guest's
  window in roughly half of all runs.
* The image is mapped `MAP_FIXED`, which silently replaces it. The loader even
  printed the collision and overwrote the memory anyway:

      [Memory] WARNING: 0x00400000+17281024 overlaps live memory ...
        overlapping: 00b38000-00bdd000 rw-p [heap]

* The crash-time map confirmed it: the client's `[heap]` was gone and the
  guest's image VMA carried the `[heap]` name.

Two fixes, both measured:

1. The loader is now linked at `--image-base 0x2000000`. The kernel derives
   `start_brk` from the last PT_LOAD, so loading the loader above the guest's
   window puts the heap permanently above it. The client is also loaded after
   the image is mapped, so brk cannot grow into the window while it allocates.
   Result: probe, 8 runs, **0 aborts, 0 overlaps** (was 4 of 6 aborting).
2. Every release path now proves ownership before it unmapping. One
   magic-tagged 16-byte header (`WINS`) is shared by both heap
   implementations; the module's `VirtualFree` asks the loader
   (`release_hook`) whether it owns the block. A guest free of a pointer it
   did not get from the loader can no longer unmap the client's heap.

The leftover `steamdrm.dll` JNE->JMP patch in `VirtualProtect` was also
removed: it rewrote the RSA-ticket gate into a direct AES decrypt, which is
the loader bypassing the DRM check itself. Steam owns verification.

Oracle unchanged: loader and Wine agree byte for byte on `""`, `"i"`, `"l"`,
and the same hashes come out of the unmodified `HEAD` sources.
Separation gate: PASSED (G1-G4).

### What the DRM handshake actually needs (measured)

Guest call sequence (`.bind` bootstrap of `FalloutNV.exe`):

    OpenEventA("Local\SteamStart_SharedMemLock")
    OpenFileMappingA("Local\SteamStart_SharedMemFile")
    WaitForSingleObject(0x30000002, 5000)
    MapViewOfFile(...)            -> writes its request at +0x90..+0xac
    CreateEventA("null")          -> 0x2001
    WaitForSingleObject(0x2001, 5000)

Measured facts:

* `"SteamStart_SharedMem"` appears **nowhere** under Proton Experimental (both
  encodings, whole tree, including the `proton` script) and **nowhere** in
  the Linux client (`linux32/steamclient.so`). The nearest real name is
  `Steam3Master_SharedMemLock`, inside Proton's prefix `steam.exe`.
* With both opens failing, as Proton does, the guest dies immediately:
  `[Steam Error] Application load error P:0000065432`.
* With the mapping handed over, the guest reads a word at `+0x90`; with it set
  to 2 the guest publishes its request. The real client never writes that
  word.
* During the 5 s wait, the real client changed **nothing** in the relayed
  object: 43 non-empty slots before, the same 43 after, 0 modified. So the
  client does not even look at the object the guest published into.
* The client's own IPC object has a different layout: header
  `[+0x0=4][+0x4=0x100][+0x8=0x200000]`, message slots at `+0x58+n*0x100`
  with `[type][token][status][peer pid]`, and per-message objects named
  `/dev/shm/u1000-Shm_<token>`.
* The process that has the real client loaded maps **no shared object at all**
  (`/proc/<pid>/maps`: zero `rw-s` regions). The shared object is created and
  owned by `steam.exe` (PID 2342457 maps it twice) and reaches the game
  through the "SteamStart" handshake, which has not happened here.

Conclusion: the object the guest wants is not the Valve IPC ring. It is an
object the client host hands over when the SteamStart handshake completes.
The bridge is one step short of it, and the missing step is the handshake
itself, not the object layout.

### Baseline: the official Steam path fails on this machine too

Running the game through Proton by hand (`proton run FalloutNV.exe`, with
`SteamAppId=22380` and the compatdata prefix) exits immediately with
`PROTON_RC=0` and never reaches the game. The Steam client's own session for
AppID 22380 (12:48:10 -> 12:48:48) behaved the same way, and the legacy
compatibility evaluator launched the game the same way. So the launch failure
the user sees from Steam's Play button is **not** specific to the WINS bridge:
the game does not start on the official path either. The exact on-screen text
is still needed to separate a licensing/DRM refusal from a graphics one.

### The "download Vulkan" prompt is Steam's shader pre-caching

`config/config.vdf` shows what Steam is actually doing:

    "ShaderCacheManager"
    {
        "CurrentBucketDriver" "...G7:VulkanPipelinesV6;..."
        "ProcessingQueue"   "22380;"
        "App" { "22380" { "ShaderCacheSize" "2045362167" } }
    }

That is Steam downloading ~2 GB of pre-compiled shaders (the `G7:VulkanPipelinesV6`
bucket) for AppID 22380 while the game starts, with a `Skip` button
(`LaunchApp_Action_SkipProcessingShaderCache`). It is not a driver check: the
host has Vulkan for both ABIs (`/usr/lib/x86_64-linux-gnu/libvulkan.so.1` and
`/usr/lib/i386-linux-gnu/libvulkan.so.1`, with the usual ICDs).

Turning shader pre-caching off (Settings -> Downloads) removes the prompt.

For the WINS side this is a separate question: WINS has no Vulkan path yet.
`native/wins_d3d9.zig` is a software rasteriser for Direct3D 9, and
`docs/HANDOFF_PELDANO1_2026-11-07.md` lists "Direct3D->Vulkan" as future work.
A Vulkan version of WINS therefore means a D3D9->Vulkan translator (DXVK's
job), not a driver installation.

## 2026-11-10 (later) — why the Play button refused: CEG integrity and hybrid-GPU presentation

Two independent faults, both measured on the installed game, not on the loader.

### 1. `Application load error 3:0000065432` was a one-byte patch in the shipped exe

`FalloutNV.exe` ships with a `.bind` section, which is Steam's CEG wrapper, and the
`.bind` blob is encrypted: `strings` on the file finds neither `SteamStart_SharedMem`
nor `Application load error`. The wrapper runs after decryption, at process start.

The installed exe differed from the reference copy by exactly one byte:

    offset 0x00000136   FileHeader.Characteristics
    installed  0x0122   (IMAGE_FILE_LARGE_ADDRESS_AWARE set, 2026-11-09 22:54)
    reference  0x0102   (stock)
    all other bytes, and every section including .bind, identical

CEG validates the executable it protects, so a patched exe is a refusal, not a crash:
the game shows `[Steam Error] Application load error N:0000065432` and exits. Restoring
0x0102 made the installed exe byte-identical to the reference copy
(`3a87f92f011e5dc9179ddf73…`) and the game launched.

Consequence for this project: the game executable is **not ours to patch**. Any WINS
work that needs a change in the PE has to be a loader-side decision, and the published
path must load a stock exe. The Steam client owns the DRM check; a loader that edits
the protected image is what produced this failure in the first place.

### 2. Black screen with audio was the adapter, not the renderer

With the exe restored, the game ran (window `"Fallout: New Vegas"`, class
`steam_app_22380`, 1920x1080, `steam.exe` shim and `lsteamclient.dll` both loaded,
DXVK 3.1.1 `d3d9.dll` native) and played audio, but the window was black.

`FalloutPrefs.ini` said:

    sD3DDevice="NVIDIA-G0"
    iAdapter=0
    iSize W=1280   iSize H=720   bFull Screen=1

DXVK enumerated three devices:

    AMD Radeon 760M Graphics (RADV PHOENIX) (radv 25.2.8)
    NVIDIA-G0 (NVIDIA 580.178.4)
    llvmpipe (LLVM 20.1.2, 256 bits)

The display is on the AMD iGPU: `xrandr --listproviders` reports
`AMD Radeon 760M Graphics @ pci:0000:06:00.0` as the sink with outputs, and
`NVIDIA-G0` as a sink with `crtcs: 0` and no outputs. Rendering on the dGPU and
presenting on the iGPU is the classic D3D9 black-window-with-sound failure.

The naming detail matters. `RendererInfo.txt` (written by the game into
`Documents/My Games/FalloutNV/`) records the device as `NVIDIA-G0`, i.e. the exact
Vulkan device name. Setting `sD3DDevice` to a shortened `"AMD Radeon 760M Graphics"`
made the game fail to find its adapter and exit. The exact string works:

    sD3DDevice="AMD Radeon 760M Graphics (RADV PHOENIX)"
    bFull Screen=0

and, if the adapter list has to be reduced to the display GPU for a whole Proton run,

    DXVK_FILTER_DEVICE_NAME="RADV PHOENIX"

at which point the game renders. The FNV launcher writes the same string itself when
its Options dialog is used to pick the adapter, which is the durable way to set it.

Consequence for this project: WINS' D3D9 layer has to report adapter names the same
way, or a game that stores its adapter by name will not find one.

### Finding the real exe instead of being pointed at a copy

`tools/steam_scan.py` reads Steam's own manifests (`steamapps/libraryfolders.vdf`
and `appmanifest_<appid>.acf`), locates the executables the app actually shipped,
picks the game binary over its launcher, and asks the loader's `--check` whether
that exact file can be loaded. It is read-only: no game directory is edited, no
executable patched, nothing written under the Steam tree.

    $ python3 tools/steam_scan.py --app 22380 --loader /home/danny/.local/opt/wins/winrun32
    [22380] Fallout: New Vegas
        exe   .../Fallout New Vegas/FalloutNV.exe  (15.8 MiB)
        check FAIL  1 unresolved import slot(s)
        run   SteamAppId=22380 .../winrun32 --run ".../FalloutNV.exe"

This matters because the CEG-protected image is the one Steam validates, so the
loader has to run the file Steam installed, not a lab copy. The scan is the piece
that finds it on any machine instead of hard-coding a path.

### DSOUND ordinal 11, and why the loader refused to run the image

The single slot that kept `--check` at FAIL was `DSOUND.dll!ordinal 11`. Two
measurements pinned it down:

1. The ordinal table in `native/winrun_ordinals.zig` maps it to
   `DirectSoundCreate8`, and the export table of Proton's real i386 `dsound.dll`
   confirms it (ordinal base 1): 1 DirectSoundCreate, 6
   DirectSoundCaptureCreate, 10 DirectSoundFullDuplexCreate, 11
   DirectSoundCreate8, 12 DirectSoundCaptureCreate8.
2. FalloutNV.exe's own import directory carries no DSOUND descriptor, so the
   slot belongs to a module the game loads at run time; the loader resolves it
   by name all the same, and with no implementation it counted the slot as
   unresolved and refused to run the image at all.

`native/wins_dsound.zig` now implements the object graph the API is: an
IDirectSound8 carrying the full vtable, IDirectSoundBuffer8 buffers over real
memory with Lock/Unlock honouring the DSBLOCK flags and wrap-around, a play
cursor advanced from CLOCK_MONOTONIC at the buffer's own byte rate, and
caps/volume/pan/frequency that answer with what was set. QueryInterface matches
the exact IIDs of the interfaces that exist here (IDirectSound, IDirectSound8,
IDirectSoundBuffer, IDirectSoundBuffer8, IUnknown); the 3D listener/buffer and
notify interfaces are refused with E_NOINTERFACE instead of handing back an
object whose vtable would not match the caller's next call.

Measured after the change:

    $ winrun32 --check ".../Fallout New Vegas/FalloutNV.exe"
    [WINS:winrun32] Check PASSED: all 280 import slots resolved.

    $ python3 tools/steam_scan.py --app 22380 --loader ~/.local/opt/wins/winrun32
    [22380] Fallout: New Vegas
        exe   .../FalloutNV.exe  (15.8 MiB)
        check ?  [WINS:winrun32] Check PASSED: all 280 import slots resolved.
        run   SteamAppId=22380 .../winrun32 --run ".../FalloutNV.exe"

What is still NOT there, so the PASS is not read as more than it is: no PCM
reaches an output device (playback is silent) and capture reports
DSERR_NODRIVER. G4 of `tools/separation_gate.sh` now asserts that the
implementation is linked into the shipped artifact and that this limitation stays
written down. G4 also had to stop asserting that DSOUND is unresolved: that was
true only while the slot was genuinely missing, and freezing a stale expectation
would have turned a real capability into a gate failure.

One shell detail worth keeping: the gate runs under `set -o pipefail`, and
`nm binary | grep -q symbol` exits 141 (SIGPIPE) the moment grep matches, which
made a PASSING check read as a failure. The gate writes nm/strings output to
files first.

Scope of this result: the import table resolves. The CEG `SteamStart_SharedMem*`
handshake is still unimplemented, so `--run` on this exe still stops at the DRM,
not at the loader's import resolution.

## Steam bridge (2026-11-10): the DRM's handshake answered by the real client

This section records what was measured while making the CEG handshake complete
against the **real** Steam client, with the loader answering for nobody. It
supersedes the "Not yet done" note above for the ticket flow: the ticket does
come from the client now.

### The CEG does not speak `SteamStart`

Under Proton the guest's whole Steam traffic was traced (`+relay` and `+server`):

| what | where | hits |
|---|---|---|
| `SteamStart` in the game trace | `/tmp/opencode/proton2/steam-22380.log` | **0** |
| `SteamStart` in the server trace | `/tmp/opencode/proton3/steam-22380.log` | **0** in 486 MB |
| `CreateInterface` calls by the guest | relay log | **2**: `SteamClient010`, then `SteamClient009` |

So the `SteamStart_SharedMem*` path is the **Steam2 fallback**, not the normal
one, and the 009 call is that fallback. The normal path is
`steam_api.dll → steamclient.dll → lsteamclient → linux32/steamclient.so →
ValveIPC → Steam`: the loader has to supply the `steamclient.dll` surface, and
the sub-interfaces have to come out of the client's own getters.

### The real client's layout, measured on `SteamClient010`

The client's global `CreateInterface` knows only the `SteamClient*` family;
`SteamUser016`, `STEAMAPPTICKET_INTERFACE_VERSION001`, `SteamUtils005` … all
answer `nil, rc=1`. Sub-interfaces only come out of the client object's own
methods:

| slot | method | shape |
|---|---|---|
| 0 | `CreateSteamPipe` | `(obj)` |
| 2 | `ConnectToGlobalUser` | `(obj, pipe)` |
| 3 | release of the (pipe, user) pair | `(obj, pipe, user)` — **validates the pair** |
| 4 | disconnect | `(obj, user)` — **one argument** |
| 5 | `GetISteamUser` | `(obj, user, pipe, name)` |
| 9 | `GetISteamUtils` | `(obj, pipe, name)` — three arguments fault inside the client |
| 13 | generic getter | `(obj, user, pipe, name)`, dispatches on the name |

The guest's calls land on exactly 0, 2, 5, 9 and 13.

### Three defects that kept the handshake from finishing

1. **`g_real_create` was never assigned.** `loadRealSteamClient()` resolved
   `CreateInterface` with `dlsym` and then forgot to store it, so every named
   interface the DRM asked for came back null. Three null interfaces is what
   made the DRM walk away from the Steamworks path and fall back to Steam2 —
   which needs the shared memory that does not exist, hence
   `Application load error P:0000065432`.
2. **The calls into the client were misaligned.** The client faults on an SSE
   store when `ESP` is not 16-byte aligned, and the guest's stack never is.
   The helpers (`callAligned0..8`) fix that; they pass the arguments through
   memory, because a thiscall caller needs `ECX` for `self` and the call
   itself clobbers `ECX` and `EDX` — Zig 0.16 refuses an inline-asm helper
   with four register inputs when it is called from a `callconv(Tc)` function.
3. **The cleanup calls were wrong.** `ISteamClient` slot 4 takes **one**
   argument, the user. The old thunk read two and forwarded
   `(pipe=1, user=0x4A2C2BF3)` — the second was stack junk from the guest.
   The client validated that pair, failed, and asserted
   `IsValidHSteamUserPipe` (`steamclient.cpp:816`); its own assert handler then
   jumped to an unmapped address and took the process down. Those two calls
   also went into the client **without** the aligned helper and **without a log
   line**, which is why the call that killed the process was invisible.

### The ticket method has its own shape, and it carries the SteamID

Measured with marker buffers against `linux32/steamclient.so`: the client's
`GetAppOwnershipTicketData` writes **one blob** and answers with **offsets**.

    blob[0..4)    = 110            length of the ticket part
    blob[4..8)    = 4
    blob[8..16)   = SteamID64      0x011000010CD725C7
    blob[16..20)  = app id         22380
    blob[110..238) = 128 bytes     RSA signature

    out[0] = 16   offset of the app id
    out[1] = 8    offset of the SteamID64
    out[2] = 110  offset of the signature
    out[3] = 128  length of the signature

The Steamworks ABI wants pointers to values and a separate signature buffer, so
the thunk translates. The SteamID64 in the blob is the account Steam has
logged in (`76561198175888903` in `logs/connection_log.txt`), and the real
client's **user object has no method that writes a SteamID64 anywhere** —
measured, every slot either faults or answers something else. So the SteamID
the DRM asks for is read from the client's own ticket, and one request answers
both of the DRM's questions.

### Measured end to end

    [WINS:Steam] ISteamClient010::CreateSteamPipe() -> real client, pipe=1
    [WINS:Steam] ISteamClient010::ConnectToGlobalUser(pipe=1) -> real client, user=1
    [WINS:Steam] ISteamUtils005::GetAppID() -> 22380 (from the real client)
    [WINS:Steam] ISteamUser016::GetSteamID() -> 0x11000010cda2607 (from the client's own ticket)
    [WINS:Steam] ISteamAppTicket001::GetAppOwnershipTicketData(appid=22380) -> 110 bytes,
                  appid=22380, steamid=0x11000010cda2607, firma=128 bytes (from the real client)
    [WINS:Steam] ISteamClient010::DisconnectGlobalUser(user=1) -> real client
    [WINS:Steam] ISteamClient010::ReleaseSteamPipe(pipe=1) -> real client, ok=1

`SteamStart` and `P:0000065432` are gone. The sub-interface tables also grew
from 24 to 64 slots: the DRM calls slots past the old end, and reading past the
array handed it a function pointer that was not code at all.

### What is NOT demonstrated

* The process still dies after the handshake, inside the **client's** assert
  handler (`EIP` in unmapped memory, the assert message is the client's own).
  The guest's own code is not proven innocent or guilty here: the client's
  handler is what faults.
* The game does not start. Nothing after the DRM handshake has been measured,
  and the loader's graphics stack is still a stub.
* The bridge is not closed: the client's assert says `IsValidHSteamUserPipe`
  fails, and that is still unexplained. A standalone probe of the same call
  sequence (same order, same arguments, same environment, even launched by the
  reaper as the game) does **not** assert, so the trigger is something the
  loader does that the probe does not.
